# Протокол монтажа: последовательно, экономно, с самоостановкой

Цель: к любому обрыву уже есть готовые проверенные видео; контекст не растёт; лимит не выбирается до упора.

## 1. Роли и контекст

- **Оркестратор** (главная сессия) тонкий: ничего не монтирует, не читает отчёты целиком, не отвечает на промежуточные уведомления. Он держит только `manifest.json` и запускает по одному видео за раз.
- **Исполнитель** (субагент, Sonnet) делает ровно ОДНО видео за запуск, свежий контекст, запускается в **foreground** (синхронно). Тогда нет уведомлений «жду фоновую работу», а значит нет пустых ходов на 700k+ контекста.
- Отчёт исполнителя: не больше 10 строк, формат ниже. Подробности он пишет в `handoff.md` задания, оркестратор их не читает.
- Оркестратор делает `/compact` после каждых 3 готовых видео или когда контекст больше 150k токенов. Не ждёт, пока он вырастет.

## 2. Манифест (единственный источник правды)

`manifest.json`, по записи на видео:

```json
{"id":"vbHY7fV2zCA","status":"todo|building|done|failed|needs_review",
 "stage":"lint|build|verify|none","out":"путь к mp4","attempts":0,
 "tokens":0,"notes":"1 строка"}
```

- Статус меняет исполнитель сразу после каждого этапа, а не в конце.
- Возобновление идемпотентно: при старте берём первое `todo`, `building` и `failed` (attempts<2). Если `out` уже существует и проходит verify, ставим `done` и не пересобираем.
- Сейчас: 16 видео, 6 готово (пачка 1 и одно ранее). Файлы пачек 2 и 3 уже частично сохранены, сначала проверить их наличие, а не собирать заново.

## 3. Порядок на ОДНО видео (исполнитель)

1. **lint плана (до сборки, без рендера).** Скрипт сверяет план Директора с лимитами набора приёмов:
   - вспышек ≤ 1, ч/б ≤ 1 (только финал), ч/б-план ≥ 2 с, смаз/заголовок только на границах блоков, whoosh только на первой границе.
   - При нарушении правит план по детерминированным правилам (а не «по ходу монтажа») и пишет в `notes` что изменено.
2. **Предпроверка объектов.** Для каждого круга/стрелки/рамки/прожектора: объект виден в кадре на этом тайм-коде и достаточно крупный. Нет → убрать приём сразу, не ставить «на глаз».
3. **Известные дефекты источника.** Список заранее: вшитый английский текст (вывески, HUD), реклама, логотипы. Где такое попадает в окно кадра, поправить кроп/окно до рендера, а не после.
4. **Одна сборка.** Рендер, rc 0.
5. **verify на готовом видео** (не на источнике):
   - кадр на каждом тайм-коде приёма (круги, стрелки, рамки, плашки, обрыв музыки), плюс по кадру раз в 8 с;
   - проверка: нет рекламы/логотипа, субтитры не перекрыты, длительность в норме, ч/б ≥ 2 с.
   - Не прошло → одна точечная перебор-пересборка (attempts≤2), дальше `needs_review` с 1 строкой причины. Бесконечных циклов нет.
6. Обновить манифест → отчёт ≤10 строк: id, файл, длительность, отклонения от плана, `needs_review`-пункты с тайм-кодами.

## 4. Очередь и параллельность

- По умолчанию **1 видео за раз**.
- Второе параллельно только если очередь сборок пуста: перед стартом проверить, сколько чужих задач впереди. Впереди есть задачи → строго 1.
- Максимум 2 исполнителя одновременно, не 3 и не пачка.
- Жёсткий потолок: не больше 1 попытки пересборки на видео в рамках одного окна лимита.

## 5. Мониторинг лимита и самоостановка

Честное ограничение: точного «остатка лимита» из сессии я не вижу. Доступны сигналы `rate_limit_event` в журнале событий (статус, тип окна `five_hour`, время сброса `resetsAt`) и код 429. Поэтому защита двухуровневая:

**Уровень 1: перед каждым видео** оркестратор проверяет последний `rate_limit_event`:
- статус не `allowed` или есть предупреждение → не запускать следующее.
- Если процент использования в событии есть: ≥ 80% → остановка, ≥ 65% → запускать только 1 исполнителя.

**Уровень 2: собственный бюджет** (если процента нет). Расход замерен: около 32k токенов субагента на видео в пачке 1, до 50k на видео в плохих условиях. Считать видео в окне; после N готовых (N задать по плану подписки, начать с 5 за 5 часов, уточнить по факту) остановка.

**Как остановиться самому:**
1. Дописать `manifest.json` (текущее видео → `todo`/`needs_review`, не `building`).
2. Записать `RESUME.md`: 5 строк, что сделано, что следующее, время сброса.
3. Запланировать возобновление `send_later` на `resetsAt` + 5 минут с текстом «продолжи по manifest.json».
4. Завершить ход без пустых ожиданий.
5. Если пришёл 429 уже посреди видео: тот же порядок, статус `todo`, не `failed`.

## 6. Запреты (то, что сожгло токены)

- Не отвечать на уведомления «агент ждёт фон». Foreground-запуск делает их невозможными.
- Не запускать пачки по 5 видео в одном субагенте: один обрыв теряет всё.
- Не ставить объекты по кадрам источника без проверки по готовому видео.
- Не править план при монтаже, правила из шага 1 применяются заранее.
- Не пересобирать готовое: сначала смотреть `manifest.json`.

## 7. Порядок запуска сейчас

1. После сброса лимита (3:10 МСК) оркестратор делает `/compact`.
2. Сверить манифест с реальными файлами в `output/2026-10-31/`.
3. Дальше цикл: проверка лимита → 1 видео → verify → манифест → следующее; остановка по уровню 1 или 2.

## 8. Методичка: как сжимать контекст и не раздувать tool uses

**Когда сжимать**
- После каждых 3 готовых видео, либо когда контекст > 150k токенов.
- Перед любой паузой/остановкой по лимиту (сжатие само тратит токены, делать до 80%, не на упоре).
- Никогда не ждать, пока сработает лимит: `/compact` при 429 падает (так было дважды).

**Как сжимать (шаблон команды)**
```
/compact Сохрани: протокол монтажа (разделы 1-6 и 8), статусы всех 16 видео из manifest.json,
id следующего видео, время сброса лимита, пути output и manifest. Отбрось: полные отчёты
субагентов, вывод ffmpeg/рендера, task-notification, таймкоды уже готовых видео, контактные листы.
```
Если `/compact` недоступен или падает: записать `RESUME.md` (5 строк), начать новую сессию, прочитать только `RESUME.md` и `manifest.json`.

**Как не раздувать контекст**
- Оркестратор не читает файлы целиком: только `manifest.json`, `tail -n 20` логов, `head` файлов.
- Вывод любой команды ограничивать (`| tail -20`, `| head -30`).
- Картинки и контактные листы смотрит только исполнитель; оркестратору возвращается строка «ок/нет + тайм-коды проблем».
- Отчёт исполнителя ≤ 10 строк, детали в `handoff.md`.
- Не отвечать на уведомления «жду»; исполнители запускаются синхронно.

**Как не раздувать tool uses (было 55–74 на пачку)**
- Бюджет исполнителя: ≤ 40 вызовов на видео.
- Склеивать команды в один вызов (`&&`), один скрипт вместо серии правок.
- Ждать сборку одним блокирующим вызовом, не опрашивать каждую минуту.
- Не перечитывать то, что уже в контексте или в манифесте.
- Превышен бюджет → статус `needs_review`, а не новая серия попыток.
